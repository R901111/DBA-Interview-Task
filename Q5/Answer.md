# 題目五：資料庫結構版本控制

## 1. 結構變更說明
我已於本次 Commit 中，透過直接修改 `Q1/Create_Orders.sql` 的建表腳本（新增了 `InvoiceNo VARCHAR(50)` 欄位），來模擬資料庫結構以檔案形式被版控與迭代的過程。

## 2. 問答題：這個變更若要套用到生產環境，你會怎麼做？
身為開發者，我會盡量避免人工連線到生產環境下 SQL 指令。我會採取以下流程：
1. **結合 CI/CD 與 Migration 工具**：使用如 Flyway、Liquibase 等版控工具，或透過 GitHub Actions / Azure DevOps 串接執行腳本。
2. **先在 Staging 驗證**：腳本必須先自動部署到與正式機同等規格的 Staging 環境，確認語法與效能沒問題。
3. **離峰時段與備份**：因為 `Orders` 是 8,000 萬筆的大表，雖然只是 `ADD COLUMN`（若為 NULLable 速度很快），但仍應選在系統離峰時段執行，並確保執行前已有近期的 Transaction Log 備份，以防萬一。

## 3. 問答題：什麼情況下，工具自動比對產生的腳本會做出你不希望它做的事？
這是我認為最需要警惕的地方，過度依賴 Schema Compare (自動比對) 工具可能會引發**災難性的資料遺失**，常見情況如下：
* **重新命名欄位 (Rename Column)**：若我將欄位從 `InvoiceNo` 改名為 `InvoiceNumber`，比對工具可能會誤判為「刪除舊欄位、新增新欄位」。如果直接執行工具產生的 `DROP COLUMN` 接著 `ADD COLUMN`，該欄位原有的歷史資料將會瞬間全部遺失。
* **資料型別縮小 (Data Type Truncation)**：若將 `VARCHAR(50)` 縮小為 `VARCHAR(20)`，工具產生的 `ALTER` 腳本可能會直接把超出的字串截斷，造成資料破壞。
* **預設值與 NULL 的衝突**：若針對有舊資料的表新增一個 `NOT NULL` 且沒有給予 `DEFAULT` 值的欄位，自動生成的腳本在執行時會直接報錯中斷。

**總結**：自動比對工具產生的 SQL 腳本，**絕對不能盲目地自動套用至生產環境，必須經過人工 Review (Code Review)**，確認它沒有使用 `DROP` 等破壞性語法後才能放行。
