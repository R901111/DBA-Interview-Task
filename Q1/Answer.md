# 題目一：訂單資料表設計與分區策略

## 1. 資料表結構設計思維
面對 8,000 萬筆的巨量資料與每日高頻寫入，我認為在設計欄位時，必須做到「錙銖必較」，盡可能縮小每一筆資料的實體大小，以節省記憶體分頁 (Page) 的空間並提升 I/O 效率：
* **OrderId / MemberId**：使用 `BIGINT` (8 bytes)，確保未來資料量無上限增長時不會發生溢位。
* **OrderNo**：使用 `VARCHAR(20)`，因訂單編號通常為英數字組合，避免使用佔用雙倍空間的 `NVARCHAR`。
* **Status**：使用 `TINYINT` (1 byte) 搭配應用程式層級的 Enum 來對應狀態，取代原本使用字串 (`VARCHAR`) 儲存狀態，可大幅減少空間並提升查詢與索引比對的速度。
* **CreatedAt**：使用 `DATETIME2(0)`，因為訂單時間通常只需精確到「秒」，不需要存到毫秒級，比傳統的 `DATETIME` 更節省空間。

## 2. 資料分區 (Table Partitioning) 策略
針對 8,000 萬筆歷史資料與每日 8 萬筆的增長，我規劃以 `CreatedAt` 作為分區鍵 (Partition Key)，並採用 **「按月分區 (Monthly Partitioning)」** 的策略。

* **為什麼按月分區？**
  每天 8 萬筆資料，一個月大約會產生 240 萬筆。這個量級對 SQL Server 來說非常健康。若按天分區會產生過多破碎的分區；若按年分區，單一分區又會太龐大（近 3,000 萬筆）。按月分區能在維護與效能間取得最佳平衡。
* **分區帶來的效益 (Partition Elimination)**：
  未來的查詢大多會帶有時間範圍（如 Q3 提到的按月查詢）。分區後，查詢引擎可以直接跳過不相干的月份分區，達到「分區修剪」的效果，極大地減少 I/O 讀取。
* **分區對齊 (Partition Alignment)**：
  為了讓資料實體存放位置與分區機制綁定，我在建立 Clustered Primary Key 時，必須將分區鍵 `CreatedAt` 納入主鍵之中，即 `(OrderId, CreatedAt)`。

## 🤖 AI 使用與決策說明

* **AI 做了哪些部分**：
  做為一名剛畢業的開發者，我過去只設計過簡單的關聯式資料表，未曾碰過 8,000 萬筆規模的巨量資料儲存架構。我將這個情境丟給 AI，請它告訴我業界處理這種大表的常見作法。AI 向我介紹了 Table Partitioning 的概念，並指導我如何撰寫 `PARTITION FUNCTION` (定義切分邊界) 與 `PARTITION SCHEME` (定義存放位置) 的語法。

* **我自己修改或否決了什麼**：
  AI 在提供分區建議時，曾提議可以「按天」進行分區以獲得最細粒度的管理。但我經過計算，一天 8 萬筆資料對 SQL Server 來說仍屬小量，若按天分區，幾年下來會產生上千個分區，反而在查詢跨月資料時會增加優化器的負擔。因此我否決了按天的建議，親自決策採用「按月」作為分區單位。此外，AI 建議將舊月份的檔案群組 (Filegroup) 放到低速硬碟，但考量到目前我的測試環境為 Docker 單機部署，我決定先將所有分區簡化存放於 `[PRIMARY]` 檔案群組中。

* **目前還不確定的地方**：
  在理論上，我設定好了目前的月份分區邊界，但在正式營運的系統中，未來每個月的分區必須透過 Sliding Window 機制（`SPLIT` 與 `MERGE`）來自動建立與封存。實務上應該要如何撰寫自動化的 SQL Agent Job 來定期維護這些分區，是我目前還未實際演練過，是我未來需要補足的實戰技能。
