# 題目四：並發下的資料一致性

## 1. 兩個請求幾乎同時進來時，會發生什麼事？
根據我對系統運作邏輯的推演，即使程式碼有寫 `IF NOT EXISTS`，但在高併發情境下，這會引發經典的 **TOCTOU (Time-Of-Check to Time-Of-Use)** 漏洞，也就是所謂的競爭危害 (Race Condition)。
按時間順序發生的情況如下：
1. **T1 (連線 A)**：執行 `IF NOT EXISTS` 檢查，資料庫回報「無紀錄」。
2. **T2 (連線 B)**：在連線 A 尚未完成寫入前，也執行了 `IF NOT EXISTS` 檢查，資料庫同樣回報「無紀錄」。
3. **T3 (連線 A)**：執行 `INSERT`，成功寫入第一筆報名紀錄。
4. **T4 (連線 B)**：因為在 T2 階段取得了允許，也執行 `INSERT`，寫入了第二筆紀錄。
**結果**：這會導致同一個 `MemberId` 與 `EventId` 產生了兩筆重複的異常資料。

## 2. 應該放在哪一層？為什麼？
我認為「不會重複」這件事的最終防護責任，必須放在 **資料庫層 (Database Layer)**。
**理由**：在過去的個人專案中，我可能只會在後端 API 寫邏輯來阻擋。但經過針對微服務與高併發架構的研究，我了解到面對網路延遲或多節點伺服器的情境，應用層的鎖（例如 Redis 分散式鎖）仍有被穿透的風險。關聯式資料庫是所有資料匯集的最後一關，只要在資料表上加上 **唯一約束 (Unique Constraint)**，底層就能硬性擋下並發瞬間的第二筆寫入並報錯。這是我認為確保資料 100% 一致性最可靠的防線。

## 3. 若已存在重複資料，加上保護措施前會先做什麼？
我查閱了建立約束的限制條件，發現在加上保護措施前，必須先清理既有的重複資料，否則建立 `UNIQUE` 約束時會直接報錯失敗。為了達成這個目的，我規劃了以下清理步驟：
* **Step 1 (查詢保留目標)**：利用 `CTE` 搭配 `ROW_NUMBER()` 視窗函數，以 `(MemberId, EventId)` 為群組，並依照報名時間 `JoinedAt` 升冪排序。
* **Step 2 (刪除重複垃圾)**：將 `ROW_NUMBER() > 1` 的紀錄刪除，確保每人每場活動只保留最早報名的那一筆真實紀錄。
* **Step 3 (建立約束)**：確認資料表清理乾淨後，立即補上 `ALTER TABLE dbo.EventJoin ADD CONSTRAINT UQ_EventJoin_Member_Event UNIQUE (MemberId, EventId);`，讓資料庫底層接管後續的防禦。

## 🤖 AI 使用與決策說明

* **AI 做了哪些部分**：
  做為一個剛踏入職場的開發者，我對高併發 (Concurrency) 造成的 Race Condition 只有基本的理論認識，缺乏實務上的防堵經驗。我將 AI 視為導師，請它向我解釋這類問題在業界的常見解法。AI 幫助我釐清了 TOCTOU 的概念，並教我如何使用 `CTE` 搭配 `ROW_NUMBER()` 這種進階的 SQL 寫法，來有效率地找出並清理重複資料。

* **我自己修改或否決了什麼**：
  AI 在討論過程中，曾提議可以在應用程式端（如後端 API）加上邏輯鎖來輔助。但我根據題目核心「責任應該放在哪一層」，以及對資料庫資料一致性的理解，決定否決將防護重心放在應用程式層的提議。我親自確立了「資料庫的 Unique Constraint 才是最後且最可靠防線」的作答主軸。

* **目前還不確定的地方**：
  雖然我透過 AI 學會了用 `CTE` 搭配 `DELETE` 來清理垃圾資料，但在真實巨量資料的生產環境中，直接執行刪除指令會不會造成系統卡頓或嚴重的鎖定 (Lock) 問題，實務上是否需要寫迴圈來「分批刪除」，這是我目前缺乏實戰經驗，未來希望能進入業界實際觀摩與學習的地方。
