# 題目三：預存程序檢視與改寫

## 1. 發現的問題（按影響程度排序）
以下是我在檢視程式碼時發現的問題，我根據理論上對效能影響的嚴重程度由高到低進行了排序，並說明為什麼將第一項視為最嚴重的問題：

1. **對時間欄位使用函數，導致 SARGable（搜尋參數化）失效（最嚴重）**
   * **說明**：原腳本在 WHERE 條件中寫了 `CONVERT(VARCHAR(10), CreatedAt, 120) >= @StartDate`。我在查閱查詢優化資料時了解到，對欄位使用函數會迫使資料庫放棄使用索引，轉而對 8,000 萬筆的 `Orders` 表進行全表掃描（Table Scan）。這會讓查詢變得極度緩慢，並嚴重消耗系統的 I/O 資源，是我認為最需要優先修正的效能瓶頸。
2. **TempDB 不當使用與過濾順序反轉**
   * **說明**：原腳本將符合日期的所有訂單全數 `SELECT * INTO #tmp`，才在下一階段用 `DELETE` 刪除不屬於該會員的資料。根據邏輯判斷，這會將巨量無用資料寫入 TempDB 後再刪除，產生不必要的磁碟 I/O 負擔。我認為應該直接在第一層查詢就透過 `MemberId` 精準過濾。
3. **隱式轉換（Implicit Conversion）引發效能耗損**
   * **說明**：傳入參數 `@MemberId` 宣告為 `VARCHAR(20)`，但 `dbo.Orders.MemberId` 型別是 `BIGINT`。雖然不影響功能，但比對時會觸發底層的型別轉換，除了增加 CPU 負擔外，也可能破壞索引的使用。
4. **Transaction 範圍過大且不必要**
   * **說明**：原程式使用 `BEGIN TRANSACTION` 將耗時的 `SELECT` 與最後的 `UPDATE` 綁在一起。透過研究鎖定 (Lock) 機制，我發現這可能會在查詢期間對資料產生不必要的鎖定，進而阻塞尖峰時段每秒 20-30 筆的正常寫入，因此建議將查詢與更新分離。
5. **低效的字串比對判斷**
   * **說明**：使用 `CHARINDEX` 來判斷狀態字串。根據查詢原則，這無法有效利用索引且比對成本較高，建議改用更現代化的寫法。

## 3. 驗證改善的方式
為了用科學數據證明改寫有效，我學到可以透過以下方式進行驗證：
* **量測方式**：我會在管理工具中開啟「包含實際執行計畫 (Include Actual Execution Plan)」，並在執行預存程序前加上 `SET STATISTICS IO, TIME ON;` 來獲取底層數據。
* **要量測與比較的指標**：
  1. **邏輯讀取數 (Logical Reads)**：觀察改寫前後對 `Orders` 表與 `TempDB` 的記憶體分頁 (Page) 讀取數量，預期改寫後數字應大幅下降，且 TempDB 的讀寫應降為 0。
  2. **執行計畫路徑 (Scan vs. Seek)**：比較執行計畫圖，確認資料庫是否成功從舊版的「叢集索引掃描 (Clustered Index Scan)」優化為新版的「索引尋找 (Index Seek)」。

## 4. 索引新增建議
**需要新增索引。** 目前 `Orders` 表只有主鍵，我建議新增以下複合涵蓋索引（Covering Index）：

```sql
CREATE NONCLUSTERED INDEX IX_Orders_MemberId_CreatedAt 
ON dbo.Orders (MemberId, CreatedAt DESC)
INCLUDE (Status, TotalAmount, OrderNo);


說明理由：
MemberId 是最常使用的精確匹配條件，所以我將它放在第一順位；CreatedAt 用於範圍過濾與 ORDER BY ... DESC 排序，因此放在第二順位。接著，我利用 INCLUDE 將 SELECT 需取出的欄位包含進來，以避免額外的 Key Lookup（書籤查閱）。因為我注意到題目提及每日有 8 萬筆新增與頻繁的狀態更新，考量到寫入時維護索引的效能成本，我判斷不宜建立過多索引，因此選擇只建立這組在讀寫之間效益最大的涵蓋索引。

## AI 使用與決策說明

* **AI 做了哪些部分**：
  做為一名剛踏入職場的開發者，我目前較缺乏千萬級別資料庫的實戰調校經驗。因此，我將 AI 視為一位「資深導師」。我將原腳本交給 AI，請它協助指出我可能沒注意到的效能盲區。AI 成功幫我點出了 `SARGable (搜尋參數化) 失效`、`隱式轉換` 以及 `TempDB 不當使用` 等底層問題，並提供了現代化語法（如 STRING_SPLIT）的改寫建議，讓我能快速對焦問題核心。

* **我自己修改或否決了什麼**：
  我並沒有全盤複製 AI 產出的程式碼，而是針對它提出的觀念進行了二次查證與釐清。例如，AI 在優化查詢時給了多組複雜的複合索引建議，但我根據題目描述「尖峰每秒有 20-30 筆寫入」，判斷過多的索引會造成嚴重的寫入負擔 (Insert Penalty)。因此我否決了 AI 過度理想化的建議，親自決定只建立一組最具效益的 `(MemberId, CreatedAt DESC)` 涵蓋索引，這是我在讀寫效能間做出的取捨。

* **目前還不確定的地方**：
  雖然從理論與執行計畫來看，目前的改寫能將邏輯讀取數降至最低，但在缺乏真實 8,000 萬筆高併發流量的測試環境下，拔除 Transaction 是否會衍生其他的鎖定 (Lock) 競爭問題，或者底層 Storage I/O 實際上是否能承受，這些都是我目前較缺乏實戰經驗，未來希望能進入業界持續精進與學習的地方。
